# Руководство тестового запуска

## Цель и границы

Поднять закрытое тестовое окружение Personal Cosmic Journal: публичный HTTPS WebApp, API/Bot и постоянный PostgreSQL. Это техническая подготовка и запуск окружения, а не приёмочное тестирование продуктовых сценариев.

В этом этапе:
- без оплаты, Premium entitlement и Telegram Stars;
- без публичного привлечения пользователей;
- без проверки сценариев Таро, натальной карты, AI-чата и ежедневного гороскопа — эти проверки начнутся после успешного запуска окружения;
- один активный API/Bot instance, поскольку текущий планировщик уведомлений ещё не имеет распределённой блокировки.

## 1. Что понадобится

- VPS в ЕС с Docker Engine и Docker Compose v2.
- Домен API с HTTPS и reverse proxy (например, Caddy или Nginx).
- Публичный HTTPS-хост для статического WebApp (рекомендуемый target — Cloudflare Pages).
- Отдельный Telegram Bot token для тестовой среды.
- AI API key и выбранный provider model.
- PostgreSQL volume с регулярными резервными копиями.

Не передавай токены и пароли в чат или GitHub. Секреты вводятся непосредственно в серверное окружение.

## 2. Подготовить конфигурацию

В корне репозитория:

```bash
cp .env.test.example .env.test
```

Заполни:
- `POSTGRES_PASSWORD` — длинный случайный пароль из букв, цифр, `_` и `-` (он вставляется в PostgreSQL URL без URL-кодирования);
- `TELEGRAM_BOT_TOKEN` — токен тестового бота;
- `SESSION_SECRET` — не менее 32 случайных символов;
- `TELEGRAM_WEBAPP_URL` — конечный HTTPS URL WebApp;
- `WEBAPP_ORIGIN` — только origin этого же хоста, без пути и завершающего слеша;
- `AI_API_KEY` и `AI_MODEL` — server-side настройки выбранной модели.

Не используй рабочий Telegram bot token или production AI key для первого тестового развертывания. Не добавляй `.env.test` в коммиты.

## 3. Собрать и запустить PostgreSQL

```bash
docker compose --env-file .env.test -f docker-compose.test.yml up -d db
docker compose --env-file .env.test -f docker-compose.test.yml ps
```

Убедись, что сервис `db` перешёл в состояние healthy.

## 4. Применить миграции

На чистой тестовой базе выполни миграции строго по порядку:

```bash
sh scripts/migrate-test.sh
```

Скрипт останавливается на первой SQL-ошибке. Повторно запускать уже применённые миграции нельзя: SQL-файлы рассчитаны на последовательную одноразовую установку, а не на повторное применение.

## 5. Развернуть API и Bot

```bash
docker compose --env-file .env.test -f docker-compose.test.yml up -d --build api
docker compose --env-file .env.test -f docker-compose.test.yml ps
docker compose --env-file .env.test -f docker-compose.test.yml logs --tail=100 api
```

Контейнер слушает только `127.0.0.1:3000` на VPS. Настрой HTTPS reverse proxy для API-домена на этот локальный порт. Не публикуй порт 3000 напрямую в интернет.

Проверь:
- `https://<API-домен>/health` — liveness, API-процесс отвечает;
- `https://<API-домен>/health/ready` — readiness, HTTP 200 и `status: ready`.

Readiness проверяет соединение с PostgreSQL, все таблицы миграций 0001–0005, Telegram Bot token/session, HTTPS WebApp origin и AI provider. При неготовности возвращается HTTP 503 с безопасными диагностическими статусами без секретов. В production API отказывается запускаться при неполной конфигурации, недоступной базе или отсутствующих таблицах.

## 6. Развернуть WebApp

В Cloudflare Pages создай проект из GitHub-репозитория со следующими настройками:

| Параметр | Значение |
|---|---|
| Root directory | `/` (корень репозитория) |
| Build command | `npm install --no-audit --no-fund && npm run build --workspace=@pcj/web` |
| Build output directory | `apps/web/dist` |
| Node version | `26.13.0` |
| Build variable | `VITE_API_URL=https://<API-домен>` |

После первого деплоя скопируй выданный Pages URL в `TELEGRAM_WEBAPP_URL` и соответствующий origin в `WEBAPP_ORIGIN` на API-сервере, затем перезапусти API. Для собственного домена WebApp используй именно его в обеих настройках.

## 7. Подключить тестового бота

После успешного старта API Bot выставит команды `/start`, `/app`, `/help` и WebApp menu button, если публичный URL корректен. Открой тестового бота и начни сессию командой `/start`.

На этом этапе достаточно подтвердить, что Bot отвечает и открывает WebApp. Проверку продуктовых сценариев и корректности результатов проводим отдельным этапом после успешного запуска.

## 8. Эксплуатационные ограничения и безопасность

- Запускай ровно один экземпляр API/Bot. Второй экземпляр может привести к дублирующим Telegram-уведомлениям.
- Уведомления гороскопа по умолчанию выключены. Не включай их массово до отдельной проверки.
- Держи PostgreSQL закрытым от внешнего доступа; volume не заменяет резервную копию.
- Настрой ежедневный backup PostgreSQL во внешнее хранилище и проверь восстановление до приглашения внешних тестировщиков.
- Ограничь доступ к тестовому WebApp и API на уровне тестового окружения/прокси, насколько это возможно без нарушения Telegram WebApp.
- Не собирай реальные чувствительные данные рождения от внешних пользователей до публикации понятной privacy notice и правил хранения/удаления данных.
- Удаление тестовой базы уничтожает историю и пользовательские записи. Перед сбросом сделай backup.
- Не добавляй платежи или тарифные ограничения в рамках этой итерации.

## Критерий успешного технического запуска

1. CI проходит typecheck, unit tests, workspace build, сборку API container и Compose config validation.
2. API container остаётся healthy, `/health/ready` возвращает HTTP 200.
3. PostgreSQL healthy; readiness подтверждает таблицы миграций 0001–0005.
4. WebApp опубликован по HTTPS и `VITE_API_URL` указывает на HTTPS API.
5. Тестовый Telegram Bot запущен, настроил команды и WebApp menu button.

После достижения этих критериев следующей отдельной итерацией начинаем пошаговую проверку основных пользовательских сценариев и фиксируем необходимые правки. Этот runbook не означает, что развёртывание уже выполнено: для этого нужны реальные секреты, домены и доступ к хостингу.
